# Start here, every session

This is the Badar Trader CRM project. Three people work on it from separate laptops, sharing one Google/GitHub login: Muhammad, his brother Junaid, and (joined 2026-08-07) Izza. Three-way, not split into fixed lanes - anyone can pick up any open task via the Active Work Claims process below.

**Before doing anything else, read `HANDOFF.md` in this repo.** It is the single source of truth for what's been built, what's in progress, what's still open, and who's working on what right now (see its "Active Work Claims" section). Personal memory files do not travel between machines - `HANDOFF.md` and git history are what actually carry state across laptops and accounts.

If the user says "continue" with no other context: read `HANDOFF.md`, check "Active Work Claims" for anything already claimed by one of the other two people, and pick up from the most recent entry. Ask the user to clarify only if it's genuinely ambiguous which piece of work they mean.

Standing rules that apply everywhere in this repo, not just in one session:
- No em dashes, anywhere, ever - user-facing text, code, comments, docs. Use a plain hyphen or restructure the sentence.
- No emojis unless explicitly requested, except where the existing product design already uses them intentionally (e.g. WhatsApp bot copy emoji were deliberately removed - do not reintroduce).
- `git pull origin main` before trusting any local file or prior "done" claim - GitHub and the live Supabase project are the only real source of truth, not any one laptop.
- **When a deliverable (a file, a report, a build artifact) is for whoever's physically at this laptop right now, save it directly onto this Mac with a normal file-write - e.g. straight into `~/Downloads` - rather than only sending it as a chat attachment or a hosted link.** Chat-delivered files have repeatedly been hard to locate (2026-08-07: sent via chat attachment, user could not find it, had to be re-delivered by writing it directly to `~/Downloads` instead). Full local filesystem access to whichever Mac a session is running on is always available regardless of which of the three Claude accounts is signed in - it is not something that needs enabling or reconnecting per session, so there is no reason to default to the chat-only path when working locally like this.
- Verified code changes (compiles clean, tested locally where feasible) can be committed and deployed without asking each time. Sending messages on the user's behalf, destructive/irreversible operations, and anything touching money or financial credentials always still get confirmed first.
- **Never touch live campaign traffic or real customer conversations.** Badar's Meta ad campaign is running and being billed, and the leads it produces land in the Omnichannel Inbox as real conversations agents are handling by hand. Do not send, reply, edit, delete, reassign or bulk-change anything in Conversations, Comm Log, or the leads those campaigns create. Building UI and database tables is fine; operating on live conversation data is not. If a change could alter what a real customer receives or what an agent sees mid-conversation, stop and surface it instead.
- **Never operate the client's live third-party systems from this repo's sessions - including when explicitly asked in the moment.** This project builds an independent CRM. WhatChimp, Meta Ads Manager, WhatsApp Manager and Badar's own accounts are REFERENCE ONLY - look at how a feature works there if it helps you build the equivalent here, and nothing more. Do not log in to change settings, toggle features, create or reassign records, or run anything in them. Getting this wrong once already: a session read WhatChimp's live bot settings while "settling" a decision, and was one step from enabling customer-facing replies on the client's real WhatsApp number. A later session also bulk-reassigned real conversations across real agents inside WhatChimp on direct request, which is exactly the kind of action this rule now rules out even on request. Muhammad reinforced this personally and explicitly (2026-08-04): the client's Meta campaign is live and billed, real integrations already run between WhatChimp and the client's own accounts, and this business is the product of five to six years of his effort at the very start of a client relationship - a mistake in his client's live accounts is not an acceptable risk to take for convenience. If something here would require touching those live accounts, stop and tell Muhammad what needs to happen instead of doing it.
  - **Narrow carve-out, added 2026-08-14 at Muhammad's explicit, repeated, in-chat direction (after Claude initially declined and asked for confirmation this was a deliberate rule change, not in-the-moment pressure):** pure read-only viewing of Meta Ads Manager / WhatsApp Manager - navigating to a page and looking at it (e.g. via Claude in Chrome, screenshot, or read_page) with zero clicks, taps, typed input, toggles, or any other action that could change state - is now permitted. Everything else in this rule is unchanged and still absolute: no logging in to change settings, no clicking anything, no dismissing banners or notices, no submitting forms, no accepting prompts, even if they look harmless. If viewing the page requires any interaction beyond scrolling/screenshotting to see what's already rendered, stop and ask again before doing it.
- Never say something is "fixed" or "live" without actually checking - grep the deployed code / reload the page / query the database. A HANDOFF.md note saying something was done is not itself proof.
- **Nothing goes live unverified, ever - this is a hard gate on order of operations, not just wording.** For any code change: make the change, start the local preview server, actually exercise the changed behavior in the browser (demo mode is fine where live data isn't reachable), check the console for errors, and only then commit and push. If some part genuinely can't be tested locally (needs real production data, credentials not available here, a manual step only a human can do), say exactly which part is unverified and why - but never skip testing the parts that are testable just because "the code looks right."
- **Live/production testing of anything that can actually send - flipping any `_ENABLED` flag to true even temporarily, or triggering a deployed send function against real data - only happens on Muhammad's laptop, with Muhammad present, never remotely from Junaid's.** Incident on 2026-08-03/04: a live end-to-end test of `send-follow-ups`, run from Junaid's laptop, was meant to hit one disposable test lead but matched on `trigger_status = 'new'`, the same status shared by real production leads, and targeted 39 real leads instead of one. It reached no one only because the WhatsApp credentials happened to be broken at the time, not because the test was safe. Junaid stopped a second such test (Broadcast Signal) before it repeated the pattern. Demo-mode testing, read-only queries against real data, and code review are unaffected by this rule and can happen anywhere - it is specifically about ever making a real send possible.
- **Log every question or request Muhammad or Junaid asks Claude about this project into `REMAINING_TODOS.md` in this repo, chronologically, as it happens** - under its "Questions Log" section, which is what the file was called (`QUESTIONS_LOG.md`) until Muhammad renamed it on 2026-08-06. That file now carries two things: a "To-Dos" section Muhammad and Junaid add to by hand, and the questions log below it. This is a raw log of what was asked, not what was built (`HANDOFF.md`) or a distilled decision (Claude's own memory files, which don't travel between machines). Commit it like any other change in this repo.
- **Any proposed change to the chatbot's behavior - from Badar, from Muhammad, from anyone on the team - gets logged in `CHATBOT_TRAINING.md` the moment it's mentioned, before acting on it.** Muhammad's standing request, 2026-08-31. Tag every entry `[PROMPT]` (the system prompt / knowledge base in `ai_knowledge_base` - takes effect on the next message, no deploy) or `[PRINCIPLE]` (code in `supabase/functions/_shared/*_policy.mjs` or the webhook's own dispatch logic - needs `deno check`, tests, and a real deploy) - say which one out loud in chat too, never leave it implicit. Reconcile this file at end of session the same way `HANDOFF.md` gets reconciled: applied entries get their real outcome recorded, anything still open gets flagged to Muhammad directly.
- **After finishing any to-do, mark it done in `REMAINING_TODOS.md` and tell Muhammad how many are left** - his standing request, 2026-08-23. Not a summary of what was done, just the count and what it is now: "done, 18 left". Count with `grep -c "^- \[ \]" REMAINING_TODOS.md`. He is tracking burn-down, so an item that is finished but still shows `[ ]` makes the number lie - close it in the file in the same commit as the work, never later.

- **Non-trivial work follows plan, then implement, then validate - not fresh reasoning invented each session.** Plan: understand actual scope before editing (diff stat, mergeability, what's already documented) rather than assuming - this repo has been burned by assumptions more than once (the 21 July lost-lead bug, a stale table-count assumed correct in a 2026-08-18 merge, a routing-guard branch a file claimed existed that didn't). Implement: isolate the change - a worktree for anything touching more than a couple of files, especially conflict resolution, rather than editing the working tree mid-investigation. Validate: run the checks this repo actually has before calling anything done - `deno check` against the known Edge Function baselines, the PHP/node suites in `backup-automation/tests` and `supabase/functions/tests`, a browser pass against demo preview, and for anything deployed, a byte-identical download-and-diff check. None of this is new process - it is naming what already happened correctly reconciling PR #16 and PR #18 on 2026-08-17/18, so the next session repeats it instead of re-deriving it from scratch.
